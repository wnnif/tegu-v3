# 安全与回滚

## 部署安全

- 每个实例使用唯一的 Compose 项目名和独立卷；数据库名为本版本 Compose 配置指定的 V3 新库。先核查主机与卷，不要接管旧网站或现存库。
- `.env` 和初始管理员密码文件仅部署账户可读，建议权限 `0600`；密码使用独立随机值，不写在命令参数、版本库、工单或日志里。
- 不公开 MySQL 3306。Web 默认只绑定 `127.0.0.1`，经 HTTPS 反向代理提供访问。公网部署要配置有效 TLS、Cookie 安全属性、防火墙、最小权限和登录访问控制。
- API 数据账号只用于当前数据库；不得给 root 或其他项目库的全局权限。日常更新不重置数据库密码、管理员密码或业务价格。
- 用户已授权公开经审核整理的工艺、公司客户收费、工人工资标准和奖金规则；V1 seed 可包含这些目录资料及有标识的 `test_only` 模拟值。未经审核的原始 Excel、真实员工身份、交易流水、密码、Token、密钥、数据库备份和本机测试凭据不得发布。V2 不含业务 seed。
- 备份需同时保护数据库快照、校验文件、附件/归档、应用数据卷 `backup.key` 和 `.env`。密钥丢失时加密云凭据无法直接恢复。
- 离机备份目录建议 `0700`，其中 `.env`、卷归档和校验文件建议 `0600`；目录和文件只授予部署管理员与明确获准的备份服务账户。数据库备份、运行数据和凭据不能提交 Git、放进公开共享目录或粘贴到聊天/工单。发布前的 seed/源码暂存目录也应限制访问，直至确认其只含获准公开的目录标准。

## 迁移风险

启动新版程序会执行其版本化数据库迁移。执行前先暂停写入、完成并校验快照，保存当前源码版本、Compose 文件、`.env`、密钥和归档文件。MySQL DDL 未必处于可整体回滚事务中；迁移中断后保留现场、检查迁移状态并使用对应版本恢复流程，不自行删除列、表或迁移编号。

导入器只用于空库首次初始化。不得通过删数据、编辑导入文件或重复换摘要来绕过校验。恢复、迁移、导入均必须明确目标项目、数据库名和卷名。

## 回滚原则

程序回退与数据库回退不是同一操作。旧代码可能不识别新结构或新业务流水；不能仅把程序目录换回旧版本继续写。推荐先保留故障现场，再将升级前快照恢复到一个新的独立 Compose 项目和空库，使用与快照匹配的源码、密钥与配置进行核验。确认恢复结果和业务增量处理方案后，才由有权限的操作者决定切换。

全量恢复命令在目标版本支持的情况下可按实际 CLI 使用：

```sh
snapshot=/backups/tegu-go-YYYYMMDDTHHMMSS-唯一编号.ndjson
docker compose run --rm --no-deps api restore "$snapshot"
```

请将示例文件名替换为实际备份文件；不要原样执行示例路径。

运行前必须确认该服务挂载到了正确的快照和空数据库；不要把它用于当前业务库或非空目标。恢复结束后核对工地、施工明细、客户票据、到账、工资/奖金余额、库存、权限、附件和加密配置。只核对表行数或成功提示不等于恢复验收。

### 独立恢复步骤

恢复演练或故障切换必须使用与快照匹配的源码版本，并建立新的源码目录、新 `.env`、唯一 Compose 项目名和全新空卷。不要在原实例目录或原业务卷执行以下命令。准备一个只部署管理员可读的恢复目录，并把本次备份中的 `instance.env`、`backups-*.tar.gz`、`app-data-*.tar.gz` 和源码放入其中；校验主机侧 `FILES.sha256`：

```sh
chmod 700 /secure/restore/tegu-v3
chmod 600 /secure/restore/tegu-v3/instance.env /secure/restore/tegu-v3/*.tar.gz /secure/restore/tegu-v3/FILES.sha256
(cd /secure/restore/tegu-v3 && sha256sum -c FILES.sha256)
```

恢复前从 `instance.env` 创建 `source/.env`（若已存在则停止并核对，不覆盖），并设置为仅部署管理员可读。通过受控编辑器把 `COMPOSE_PROJECT_NAME` 改成新的唯一名称，并为 `HTTP_PORT` 选一个未占用端口；保持数据库名称及数据库密码与快照实例兼容。不要回显 `.env`。随后启动新项目的 MySQL、创建结构，并将两个卷归档解到这个新项目创建的卷：

```sh
set -eu
cd /secure/restore/tegu-v3/source
test ! -e .env
cp ../instance.env .env
chmod 600 .env
docker compose build api web
docker compose up -d --wait mysql
docker compose run --rm --no-deps api init-db
backup_archive=/secure/restore/tegu-v3/backups-YYYYMMDDTHHMMSSZ.tar.gz
app_archive=/secure/restore/tegu-v3/app-data-YYYYMMDDTHHMMSSZ.tar.gz
docker compose run --rm --no-deps -T --entrypoint sh api \
  -c 'tar -xzf - -C /backups' < "$backup_archive"
docker compose run --rm --no-deps -T --entrypoint sh api \
  -c 'tar -xzf - -C /var/lib/tegu' < "$app_archive"
```

将两个变量的时间戳替换为同一份备份集中的实际文件名；恢复前再次确认 `COMPOSE_PROJECT_NAME` 是新名称。

在新项目的 `/backups` 中选出已校验的 `.ndjson` 快照，再恢复到刚初始化的空数据库：

```sh
snapshot=/backups/tegu-go-YYYYMMDDTHHMMSS-唯一编号.ndjson
docker compose run --rm --no-deps api restore "$snapshot"
docker compose up -d --wait
docker compose ps
```

把 `snapshot` 替换为刚解包并校验的实际快照名。命令完成后再继续应用验收。

`restore` 命令本身会核对同名 `.sha256` 并拒绝非空业务表；恢复数据库后不要执行 seed 导入或重置管理员。确认 `app-data` 与数据库快照来自同一备份时点，才能保留原云凭据解密能力。月度归档文件随 `/backups` 卷恢复；若只恢复了单独下载的数据库快照而没有卷归档，需明确记录月度文件缺失，并由恢复环境重新生成可生成的归档。最终逐项检查登录权限、业务金额与余额、工资/奖金、附件、密钥可读性、归档文件和服务日志，再由有权限的操作者决定是否切换流量。

禁止执行 `docker compose down -v`、`docker volume prune`、手工删除 MySQL 数据目录或通过清空表完成回滚。若恢复目标、迁移状态或备份匹配关系不清楚，停止并升级给系统维护人处理。
